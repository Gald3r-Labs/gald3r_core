    gald3r_core — Product Docs¶

    This is the end-user product documentation for gald3r_core: the thing you install and run to get task/bug tracking, agent runs, and the CRASH (Commands/Rules/Agents/Skills/ Hooks) system in your own project. It is deliberately separate from this repo's contributor docs (root README.md, AGENTS.md, CONTRIBUTING.md), which describe how to work on gald3r_core itself, not how to use the finished gald3r command in a project of your own.

    Runs on Windows, macOS, and Linux. One CLI, three platforms — signed Windows binaries (.msi + dual-exe), a macOS .pkg (notarized binary), and a Linux tarball installer ship from every release. See Install for the per-OS quick start.

    What is gald3r?¶

    gald3r is a single-binary CLI coding-agent platform: a task/bug tracker, a multi-provider agent runtime (local models via Ollama/LM Studio/vLLM, or cloud providers), and the CRASH component system (Commands, Rules, Agents, Skills, Hooks) that turns those into enforced, executing behavior in a project — not just markdown instructions an LLM might follow.

    It is built to be comparable to tools like Claude Code, Cursor's agent, or OpenCode, but standalone: one binary, no required IDE.

    Who this is for¶

    • Someone who wants to use the gald3r command in their own project (task tracking, agent runs, project scaffolding).
    • Someone evaluating gald3r_core as a product, distinct from the frameworks/templates it absorbs capability from.

    If you are instead working on gald3r_core's own source code, start with the root AGENTS.md and CONTRIBUTING.md instead — this directory is not for you.

    Honest status (as of this writing, 2026-08-05)¶

    • gald3r_core is 4.0.0, in public beta (v4.0.0-beta.3 is the current release). Some verbs are fully wired, some are stubs, some depend on optional network services (world_tree). This doc set only documents what was verified working by actually running the commands — see each page for specifics, and treat anything not shown running here as unverified.
    • Signed binary releases exist and are the recommended install path. Every release attaches signed binaries and per-OS installers for all three OSes: Authenticode-signed Windows .exe/.msi, a codesigned + Apple-notarized macOS .pkg (container-signed with Developer ID Installer and stapled), and a checksum-verified Linux tarball — see install.md. Building from source is a contributors-only path (the source repo is private).
    • No PyPI package. gald3r-core is not published to PyPI; pip install gald3r-core does not work. Don't tell users to do that until it's true.

    Scope note¶

    This directory's Markdown is also wrapped in a real generated static site (MkDocs + Material, T485; expanded T564) — see "Building the docs site locally" below. The Markdown itself remains the source of truth (readable directly on GitHub, no build step required to read it); the site is a richer presentation of the same pages with navigation and search. docs/product/'s introduction task (T69) deliberately shipped Markdown-only first and wrote the original four pages so a generator could be pointed at this folder later with minimal rework (README.md as the index/home page, one topic per file, relative links only) — T485 was that follow-up, and T564 is the content-depth follow-up to THAT: per-platform install, a full first-project walkthrough, CRASH explained with real examples, the full task/bug lifecycle, autopilot/swarm coordination, Valkyrie/WPAC multi-project coordination, memory, and plugins/skill packs — each page built from commands actually run against this repo (or a disposable scratch project), not written from memory.

    Docs site publishing (T564)¶

    What's live today: the MkDocs Material build itself (uv run mkdocs build --strict, verified passing in this repo's own CI-equivalent local run) and a GitHub Actions workflow (.github/workflows/docs-publish.yml) that builds this site and publishes it to the public Gald3r-Labs/gald3r_core repo's gh-pages branch, under a version-labeled subdirectory (/4.0/, plus a /latest/ alias), whenever a v* release tag is pushed to gald3r_core_dev — the same private-build/public-publish pattern .github/workflows/binary-build.yml already uses for the compiled binaries, reusing the same RELEASE_PAT secret.

    What is NOT live, and why it's outside this repo's reach:

    1. The docs.gald3r.ai DNS record and GitHub Pages custom-domain configuration on the public Gald3r-Labs/gald3r_core repo — both are one-time manual setup steps on infrastructure this repo's CI does not have access to (DNS is not code in this repo; GitHub Pages settings are a repo-admin UI action, not something git push triggers).
    2. Whether gald3r_web (a separate sibling repo — see .gald3r/linking/link_topology.md) ends up serving these docs itself instead of GitHub Pages, e.g. if docs.gald3r.ai should live inside gald3r_web's own Cloudflare Pages/Next.js stack rather than a bare static GitHub Pages site. That is gald3r_web's decision to make, not gald3r_core_dev's — this repo notified gald3r_web of the finished content + the CI-publish shape via the WPAC INBOX (INFO-002, see that repo's .gald3r/linking/INBOX.md) so the two teams can decide together rather than gald3r_core_dev unilaterally claiming a domain it doesn't own.
    3. No v* tag has been pushed yet, so docs-publish.yml has never actually run for real — it is written, syntax-validated, and follows the exact pattern of the already-working binary-build.yml, but is unverified end-to-end until the first tagged release.

    Versioning: each publish lands under /<major>.<minor>/ (matching the 4.0 line today) plus a /latest/ alias that always points at the newest release — so a docs URL for a given release line stays stable even as patch releases ship, without needing a heavier multi-version tool (e.g. mike) wired in before there is a second version to actually distinguish.

    Building the docs site locally¶

    The site config lives at mkdocs.yml (repo root) and builds every page in this directory (see the "Where to go next" table above for the full list) into a searchable static site with Material for MkDocs navigation. It does not include this repo's contributor docs (root README.md/AGENTS.md/CONTRIBUTING.md) — see the scope note above for why those stay separate.

    # One-time: install the docs build tooling (kept out of the default `uv sync`
# dev group since it's only needed when building/serving the site — see
# pyproject.toml's [project.optional-dependencies].docs)
uv sync --extra docs
# or: uv pip install mkdocs mkdocs-material

# Build a static site into ./site/ (gitignored — never commit build output)
uv run mkdocs build --strict

# Or serve it locally with live-reload at http://127.0.0.1:8000
uv run mkdocs serve

    mkdocs build --strict is the verification command — it fails the build on any content warning. Links from these pages out to the repo-root contributor docs (../../README.md, ../../AGENTS.md, ../../GALD3R.md, ../../CONTRIBUTING.md) are expected to resolve outside docs_dir; mkdocs.yml's validation.links config downgrades that specific, known pattern from warn to info so the build stays clean without masking genuine in-site broken links.
