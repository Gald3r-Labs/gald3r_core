    gald3r_ide -- a code editor that shows you the diff¶

    gald3r_ide is a standalone desktop code editor. It shares one editor core -- @gald3r/editor-core -- with Gald3r Throne's built-in IDE section, so the two apps are never two separate implementations of the same editor: they are two hosts around the same package.

    Why this exists¶

    In the owner's own words, requesting the epic this page documents:

    "I need it to be someplace between notepad++/ultraedit and vs code. VS code is overkill for what I want here... I do not need all of the plugin/marketplace/extensions of vs code... I need to be able to edit code, and interact with an ai agent. have it interact with the code files, show diffs for me to accept... something that will appeal to the developers and programmers who don't want to not see the code (like me, I want to see the code changes, biggest complaint I have with Claude Code, Codex, New Cursor)... I am thinking an early days version of VS Code, back when it was more like (but more advanced) than notepad++ and ultra-edit, but still have syntax highlighting, language files with syntax, code folding etc."

    -- task1326 requestor_verbatim, 2026-09-02

    That "I want to see the code changes" complaint is not a stray preference. It is the same gap docs/port/VISION_MASTER.md section 2.7 item 10 names directly, citing the owner's own YC framing:

    "The evidence does not support [coordination] as the wedge... The verification ladder... is the most-tested and most-differentiated part of the system... and appears on no slide."

    gald3r_ide is that verification ladder built into an editor. Every AI-proposed change is rendered as a diff, and nothing reaches disk until a human accepts it -- hunk by hunk.

    Positioning: Notepad++ / UltraEdit .. early VS Code¶

    gald3r_ide deliberately targets the band between a fast plain-text editor and VS Code circa 2016 -- before the extension marketplace took over that product's identity. In scope: syntax highlighting from per-language definition files, code folding, comment toggling, find/replace, multi-tab editing, a file tree, a settings page, and an AI agent panel that edits files through a visible, per-hunk-acceptable diff. See Non-goals for what is deliberately left out.

    One editor core, no fork¶

    Throne's code editor, file tree, tabs, diff viewer, search surfaces, settings page, and keybinding system all live in one npm workspace package -- @gald3r/editor-core (gald3r_throne/frontend/packages/editor-core/). Both Throne's IDE section and gald3r_ide import this package as a workspace dependency; neither copies or forks its source. Concretely, the package exports:

    • the CodeMirror 6 editor surface, file viewer, and conflict-on-save prompt
    • the file tree and open-file tab strip
    • find/replace, find-in-files, go-to-line, and quick-open
    • the diff viewer and per-hunk accept/reject UI
    • the AI agent panel and its tool contract
    • the settings page and its keybinding-preset system
    • 25 per-language definition files driving syntax, folding, and comment tokens

    A small HostFileIO interface is the seam between the package and whichever app embeds it: Throne backs it with its own multi-project file bindings; gald3r_ide backs it with a slimmer binding scoped to a single opened folder. Shared CSS custom properties keep both apps' editor surfaces visually identical -- theme-token sharing between the two apps is in progress (T1337) rather than fully landed.

    Seeing AI edits before they touch disk¶

    The agent panel never writes a file directly. Every proposed change goes through the same path a human edit does:

    1. The agent proposes an edit -- full replacement content or a patch -- through the package's tool contract. This step only proposes; it does not write anything.
    2. The proposal renders as a unified diff in the same diff viewer Throne already uses for Stage/Unstage/Revert and its merge-conflict panes.
    3. Each hunk gets its own Accept/Reject control. You can take some hunks from a proposed change and leave the rest.
    4. Only accepted hunks are written, through the same save path (and the same conflict detection) a manual edit goes through.
    5. What was proposed, accepted, and rejected is recorded in an append-only approvals ledger, so there is always a record of what the agent asked to do and what you actually let through.

    The same approval discipline covers the agent running a command: a proposed command is queued for your explicit approval before it executes -- the agent cannot invoke a command directly, the same way it cannot write a file directly.

    Language files you can read and extend¶

    Syntax highlighting, code folding, and comment-toggle tokens are driven by one JSON file per language, not by logic buried in TypeScript. They live at gald3r_throne/frontend/packages/editor-core/src/languages/defs/ -- 25 languages today, including several CodeMirror has no first-party pack for (Shell, PowerShell, SQL, TOML, Batch, Dockerfile, git config/ignore files, TOON, and the PL/SQL, PostgreSQL, SQLite, and DuckDB SQL dialects). Each definition carries the file extensions it matches, its folding strategy, and its line/block comment tokens. The editor settings page's Language Files section lists the registry and lets you map an unrecognized extension onto an existing language pack, without touching source.

    Keybindings¶

    Three presets ship out of the box -- VS Code (the default), Notepad++, and UltraEdit -- switchable live from the editor's right-click menu or the settings page, and remembered per user. Picking a preset does not require relearning muscle memory built up in whichever of those three editors you already know.

    Settings¶

    One settings page, shared by Throne's IDE and gald3r_ide, covers:

    • Fonts -- family and size
    • Theme -- light / dark / system, following the same token set the rest of the app uses
    • Keybindings -- the preset picker above
    • Language files -- the registry, with per-extension overrides
    • Agent provider -- which credential and model backs the agent panel, reusing the same provider/credential discovery Throne's own AI settings already use

    Using it¶

    gald3r_ide <path>
    • A file path opens that file, with its containing folder as the file-tree root.
    • A folder path opens that folder.
    • No argument reopens whatever folder you had open last, or shows a folder picker if nothing is remembered yet.

    Windows: "Open with gald3r_agent" (forthcoming)¶

    Right-click shell integration -- an "Open with gald3r_agent" entry on files and folders in Windows Explorer, wired to gald3r_ide.exe -- is specced and in progress, not yet shipped. It is designed around two entry points: gald3r_ide --register-shell / gald3r_ide --unregister-shell flags that write and remove the registry entries directly, and a Windows NSIS installer (a sibling of Throne's own installer) that calls those same flags at install/uninstall time, so there is exactly one implementation of what gets written to the registry.

    Non-goals¶

    gald3r_ide is intentionally not trying to become VS Code. Out of scope, by design:

    • No extension or plugin marketplace, and no third-party extension API of any kind.
    • No remote-dev (SSH/container) targets.
    • No multi-root workspace concept -- opening another folder replaces the currently open one, it does not add to it.
    • No reimplementation of Throne's world_tree auth, swarm observability, avatar/theatre-voice, addon installer, or workspace-graph surfaces -- those stay Throne-only.
    • No new diff algorithm -- the existing unified-diff engine is reused as-is; the new surface is the accept/reject-per-hunk UI and the apply-on-accept wiring around it.
