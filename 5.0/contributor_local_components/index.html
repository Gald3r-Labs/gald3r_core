    Contributor-local components, and how a canon component gets retired¶

    task1208, slices (a) and (d). Written directly from the owner's own verbatim question that opened this task: "can I start putting my extra skills into the .claude and .cursor folders here or are they still used as the basis of what ships" and "how do we retire old gald3r CRASH, or does it just get left out there and might be causing behaviour issues?" This page is the answer to both, and the two turn out to be one lifecycle gap, not two.

    What actually ships¶

    Only one tree is the source of truth for what a gald3r platform install/gald3r sync run projects into a project's .claude/.cursor/etc. folders: the package-embedded neutral component set under gald3r_platforms/assets/neutral_source/{commands,rules,hooks,agents,skills} (the Go port; the historical Python source is src/gald3r_core/platform/pipeline/neutral_source/ — see gald3r_platforms/generate/overlay.go's own doc comment for the "one convention only" architectural note). gald3r.ai/platforms/generate. GenerateOverlay reads that tree and nothing else, and projects it per-platform through each profile.PlatformProfile's layout map.

    This repo's own .claude/ and .cursor/ folders are not a second source of truth. They are this checkout's own dev-tool install of that same neutral component set — the same overlay a consumer project ends up with, kept current via gald3r sync (gald3r_cli/internal/commands/ sync.go, gald3r_maintainer-build-tag-gated, checkout-only). Editing a file inside this repo's .claude/rules/g-rl-43-*.md directly, instead of editing neutral_source/rules/g-rl-43-*.md and re-running gald3r sync --apply, edits a copy that the next sync will either overwrite (if neutral_source never caught up — BUG-1339's own regression guard now catches and flags that case rather than silently reverting it) or leave stale forever (if nobody remembers this checkout even has its own drifted copy). Either way, a canon-named file is the wrong place for one-off local content.

    Can I add my own personal skills/rules locally? Yes — with one naming rule¶

    Yes. A contributor (this repo's owner very much included) can drop a personal, draft, or scratch component directly into this repo's .claude//.cursor/ folders, or into any installed consumer project's own overlay folders, without going anywhere near neutral_source. It will never be shipped, never be synced away, and never collide with a canon component — as long as it does not use the "g-" naming prefix.

    Every canon CRASH component this project ships is named with a "g-" prefix: g-status, g-rl-43-gald3r-search-mandate, g-skl-tasks, g-agnt-verifier. That prefix is the entire contract. A personal component should use anything else — your own initials, a project codename, plain English (wrm-scratch-notes, my-local-helper, draft-idea-tracker). This is enforced in exactly one automated place today (gald3r_platforms/pipeline.IsCanonicalComponentName, task1208d): it decides which basenames are even eligible to be listed in the tombstone-retirement registry below, so a personal file can never accidentally become a deletion target — see "How retirement stays safe" below for why that matters beyond naming hygiene.

    How parity/drift audits treat a personal component: list, never flag¶

    gald3r sync's drift report (this repo's own dev-tool resync) already separates its findings into to_add / to_change / identical / orphaned / guarded. A personal, non-canon component sitting inside a swept component directory (e.g. .claude/rules/wrm-scratch-notes.md) shows up as orphaned — present on disk, not part of the generated overlay — and sync.go's own doc comment is explicit that orphaned paths are "only ever reported, never deleted" even with --apply. There is no --prune in this Go port at all (see sync.go's "Scope trim" note). gald3r doctor follows the same posture: every check this task adds or touches (user_mod_pairing, tombstone_retirement) reports warn at worst, never fail — resolving either is framed as a deliberate human decision, not an automatically-corrected defect.

    In short: an orphaned listing is informational. It is not a parity gap, not a lint error, and never blocks a sync or an install. If you are building tooling on top of gald3r sync --json's orphaned array, do not treat a non-"g-"-prefixed entry as a problem to fix — that is exactly the contributor-local shape this contract exists to protect.

    Retiring a canon component: the tombstone registry¶

    Before task1208, there was no way to actually remove a canon component from an already-installed project. Deleting a rule from neutral_source (as task1195 did for g-rl-09-python_venv.md, once the product stopped being Python/UV-based) only ever stops it from being written to new installs — every project that had already run platform install before that change keeps the retired file forever, still always-applying, with no cleanup path. That is the "does it just get left out there" half of the owner's question, and the answer used to be yes.

    gald3r_platforms/pipeline/tombstones.go's RetiredOverlayPaths registry closes that gap. It is an explicit, owner-curated list — never inferred from "not in the current overlay" (that would risk treating a contributor's personal file as a retirement target the moment its name happened to collide with a stale sweep). Retiring a canon component going forward means adding one entry per affected platform:

    {
    Platform: "claude",
    RelPath:  ".claude/rules/g-rl-09-python_venv.md",
    Reason:   "task1195 (2026-08-25 owner ruling): the product is no longer Python/UV-based; ...",
}

    From that point on, every gald3r platform install (default behavior; opt out with --no-retire-tombstones) deletes the file only when all three of these hold — see pipeline.ApplyTombstoneRetirement's own doc comment for the full mechanism:

    1. tombstoned — explicitly listed in RetiredOverlayPaths for this platform.
    2. manifest-tracked — this platform's install-provenance ledger (pipeline.UserModLedgerPath, the same ledger task1208(b)'s --preserve-user-mods reads) has a recorded baseline for this exact path, i.e. gald3r itself is proven to have written it.
    3. content-hash-matches-shipped — the current on-disk bytes still hash to that recorded baseline. Any mismatch means something (almost certainly the user) touched the file since gald3r last wrote it, and it is reported (guarded_user_modified) but never deleted.

    A retired path with no ledger entry at all (skipped_not_manifest_tracked) is likewise never deleted — no proof of gald3r authorship means no deletion, full stop, mirroring ClassifyUserModifiedPaths' identical fail-closed posture on the overwrite side.

    How retirement stays safe against the contributor-local case¶

    The two halves of this task lock together on purpose: RetiredOverlayPaths can only ever name a path whose basename is canon-shaped (IsCanonicalComponentName returns true) — TestRetiredOverlayPaths_AllEntriesUseCanonicalNaming in gald3r_platforms/pipeline/tombstones_test.go fails the build the moment a non-canonical path is ever added to the registry by mistake. Combined with gate (1) above (a path must be explicitly listed, never inferred), a contributor's personal wrm-scratch-notes.md living in the exact same directory as a retired canon rule is structurally never a deletion candidate — it is simply never named anywhere the deletion logic looks.

    Surfacing: gald3r doctor's tombstone_retirement check¶

    Running gald3r doctor on any project reports a tombstone_retirement check (always warn, never fail) naming every RetiredOverlayPaths entry still present on disk, whether it would be cleaned up automatically on the next install (would_delete) or needs a human look (guarded_user_modified, skipped_not_manifest_tracked). A clean project (nothing retired ever installed there) reports ok.

    Quick reference¶

    Question Answer
    What actually ships to a consumer project? Only gald3r_platforms/assets/neutral_source, projected by generate.GenerateOverlay.
    Can I add my own local skill/rule to .claude/.cursor? Yes — name it without the g- prefix.
    Will gald3r sync/doctor complain about my local component? No — it is listed (orphaned), never flagged as an error, never auto-deleted.
    How do I retire a canon (g--prefixed) component for good? Delete it from neutral_source AND add an entry to pipeline.RetiredOverlayPaths for every affected platform.
    Will retirement ever delete a file I modified? No — guarded_user_modified is reported, never deleted.
    Will retirement ever delete my personal component? No — only paths explicitly named in the registry are ever candidates, and the registry may only carry canon-named paths.
